# Safe generation and extension points

Phase 10's 8-item checklist, closed in `internal/generators/write.go` (new)
and a refactor of `internal/generators/engine.go`'s write paths. Every
claim below was verified against real generation runs — determinism,
mtime-stability, and the dry-run/diff output were all actually observed,
not just implemented and assumed correct — and the full output still
compiles against the pinned GameAK revision
(`tests/project_mode_test.go`'s `TestScaffoldModesCompile`).

## 1. Atomic file writes

`atomicWriteFile` (`write.go`) writes to a temp file in the same
directory, then `os.Rename`s it into place — atomic on the same
filesystem on both POSIX and Windows. Every generated `.hpp`/`.cpp` write
goes through this (via the `writeSink` interface, see §6) instead of the
previous `os.Create` + `tpl.Execute` directly into the destination file,
which could leave a truncated file behind if the template panicked or the
process was killed mid-write. A render error is now caught *before* any
file is touched (rendered into an in-memory `bytes.Buffer` first), so a
bad template can't corrupt an existing good file at all, atomic write or
not.

## 2. Distinguish generated vs. user-owned files

Every fully-generated file (`.hpp` headers, the block registry) now
starts with:

```cpp
// Code generated by seed v0.1.0 from Models/Component/Position.yaml. DO NOT EDIT.
```

Every user-owned file (a System's `.cpp` skeleton, created once and never
touched again — §3) starts with a different, one-time note instead:

```cpp
// Generated once by seed from Models/System/Gravity.yaml; edit freely below.
// seed will not overwrite this file again — delete it to regenerate.
```

The header text itself *is* the distinguishing marker — a human (or a
future tool) can tell which category a file is in by its first line alone,
without cross-referencing a separate manifest. Neither header includes a
timestamp: a build timestamp would make two syncs of identical models
produce byte-different output, which would break §7's reproducibility for
no benefit a content diff doesn't already give.

## 3. Preserve manual system implementations

Already true before this pass (`writeCpp` already skipped existing files)
and now formalized as `writeOnceSink` (`write.go`): a sink wrapper that
checks `os.Stat` before ever calling its inner sink, so a System's `.cpp`
is written exactly once, on first `seed sync` after `seed generate
system`, and never again — verified in `tests/generation_safety_test.go`
by hand-editing a generated `.cpp`, re-running `Sync`, and confirming the
edit survived byte-for-byte.

## 4. Stable hooks for custom C++ behavior and backend-specific overrides

No new mechanism was needed — this phase's job was confirming and
documenting the ones that already exist, together, as "the hooks":

- **System `.cpp` implementations** (§3) — the primary escape hatch for
  gameplay logic: `seed` generates the `.hpp` interface and a `.cpp`
  skeleton once; everything inside is hand-written C++ forever after.
- **Cardinal's named guard/action extension points** (Phase 6,
  `docs/cardinal.md` §7-9) — a transition's `guard: {name: ...}` or a
  state's `entry`/`exit` list names a C++ function the author implements;
  Seed only ever generates the *call site* shape, never the guard/action
  body.
- **`bootstrap.cpp`'s `@seed:begin(...)`/`@seed:end(...)` blocks**
  (`internal/generators/engine.go`'s `replaceSeedBlock`) — the one place
  inside an otherwise-regenerated file that's actually a stable,
  programmatically-managed region: registration calls are rewritten
  between the markers on every sync, but nothing outside them is ever
  touched, so hand-added bootstrap code (additional init order, extra
  registrations) survives.

## 5. Detect stale and orphaned files without deleting user files

Already true and unchanged by this pass, confirmed by re-reading
`internal/commands/doctor.go` end to end: `checkOrphanedFiles` and
`GetSyncStatus`/`CheckSync` (`internal/generators/analysis.go`,
`engine.go`) are both purely read-only — neither calls `os.Remove` or
`os.RemoveAll` anywhere, verified by grep, not just by reading the
intent. They report; nothing in this codebase auto-deletes a generated
file, orphaned or not — a human has to run `seed model delete` (or delete
by hand) to remove anything.

## 6. Dry-run/diff mode

`seed sync --dry-run` (`internal/commands/sync.go`, backed by
`generators.SyncPlan`) runs the **exact same compile-and-render pipeline**
`Sync` does — same `Compile`, same templates, same rendering — but every
write goes through `dryRunSink` instead of `diskSink`: it compares the
freshly rendered (and clang-formatted, see §7's note) content against
what's already on disk and records a `FileChange{Path, Action, Diff}`
instead of touching the filesystem. This is a real preview, not an
approximation that could drift from what `Sync` actually does, because
both paths share every line of rendering code — only the final `sink.write`
call differs.

The diff itself (`internal/generators/difftext.go`) is a small
line-level LCS diff producing familiar `diff -u`-style `@@`/`-`/`+`
output — not an external dependency, since generated files are small
enough (well under the input sizes where an O(n·m) LCS would matter) for
a straightforward implementation to be fast in practice.

**Known gap, stated plainly:** `--dry-run` previews every `.hpp`/`.cpp`
write but not `bootstrap.cpp`'s registration-block changes (§4) — that
file is rewritten in place unconditionally today, not yet routed through
a sink. Left out of this pass rather than half-implemented; the
registration lines it would show are already visible via `seed inspect
models`/`schedule`.

## 7. Reproducible generation across machines and repeated runs

Verified directly, not just argued: `scanAllModels` walks `Models/`
via `os.ReadDir`, which — unlike map iteration — already returns entries
sorted by filename, and nothing in the render path iterates a Go map to
produce output order (checked every `range` over a map in
`internal/generators/*.go`; none affect generated file content or order).
Confirmed empirically: deleting `Include/`/`Src/` and re-running `Sync`
twice in a row produces byte-identical output on every file
(`tests/generation_safety_test.go`'s determinism test, and a manual
`sha256sum` comparison across two full resyncs of the `docs/examples`
domain while implementing this).

This is also why formatting was moved from "run `clang-format -i` on the
file after writing" to `formatBuffer` — clang-format applied to an
in-memory buffer *before* comparison, not to the file *after* writing —
see §6/§8: comparing an unformatted freshly-rendered buffer against an
already-formatted on-disk file would have made both the "skip an
identical write" optimization (§1) and the dry-run diff (§6) see
spurious formatting-only differences on every single sync, a real bug
caught while implementing this and fixed before it shipped.

## 8. Generated-file headers and provenance metadata

Covered by §2's headers: every generated file's provenance is the exact
`Models/` YAML path it came from, plus the tool version
(`generators.SeedVersion`, currently `"0.1.0"`, kept in sync by hand with
`rootCmd.Version` in `internal/commands/root.go` — both currently read
the same value; a single shared version source is a reasonable follow-up,
not done here to avoid restructuring the package dependency direction for
a one-line convenience). The block registry header
(`Include/<ns>/BlockRegistry.hpp`, generated from multiple Block YAML
files at once) instead cites `Models/Block/*.yaml`, since it has no
single source file — provenance metadata that's honest about a many-to-one
generation relationship rather than picking an arbitrary single source.
